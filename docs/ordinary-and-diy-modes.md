# 普通版 / DIY 版本地 Agent 模式

本文是 `project-knowledge-officer` 的双模式使用规格。目标是让普通白领可以在 Codex 或其他本地通用 Agent 中管理会议和项目知识，同时保留给愿意动手的用户自行调整模板、分类、脚本和版本策略的空间。

第一版不做云端产品，不要求用户手敲命令。命令行脚本、Git、校验和 artifact manifest 是 Agent 背后的可靠性机制，不是普通版用户必须理解的入口。

## 两个用户可见模式

### 普通版

普通版是默认模式。用户只需要理解 4 个概念：

| 概念 | 用户需要知道什么 |
| --- | --- |
| 项目文件夹 | 某个项目的会议和项目知识都保存在一个本地文件夹中。默认建议路径是 `~/MeetingKnowledge/<project-id>-knowledge`，用户可以指定其他路径。 |
| 待处理材料 | 新会议的文字、录音、PDF、PPT、图片、用户补充信息或用户指定检索的邮件都可以交给 Agent 处理。 |
| 当前项目状态 | Agent 会维护项目当前总结、决定、待办、未决问题和时间线。 |
| 来源证据 | 重要结论都要能追到会议、附件或来源 artifact，不能只靠记忆或猜测。 |

普通版中，Agent 负责执行目录创建、模板填充、校验、本地版本保存和来源追踪。用户不需要理解 `metadata.yaml`、`rollup`、`manifest`、`validate-project`、`commit`、`minimal` 或 `advanced`。

### DIY 版

DIY 版面向愿意理解和改造机制的用户。Agent 可以解释并协助调整：

- 项目知识仓库目录结构。
- `project-config.yaml`、Domain/taxonomy 和模板。
- `prompts/`、`templates/`、`checklists/` 和脚本参数。
- 本地 Git、提交边界、校验规则和 artifact 策略。
- portfolio/index、legacy vault 或迁移流程。

DIY 版不是能力等级标签，而是“用户想自己动手配置和维护”的工作方式。

## 默认交互协议

除非用户明确要求 DIY、配置、排错、审计、模板调整或协作策略，Agent 默认按普通版协作。

### 普通版首次项目初始化

Agent 最多只把下面内容作为用户确认入口：

1. 项目叫什么？
2. 使用普通版还是 DIY 版？
3. 默认隐私确认：此项目默认只给你本人本机使用；如果以后要共享给同事，我会先帮你检查敏感附件和共享范围。是否按这个默认设置？

项目知识文件夹路径不作为普通版必答问题。默认使用 `~/MeetingKnowledge/<project-id>-knowledge`；如果用户给了路径，以用户路径为准。

### 普通版单场会议入库

Agent 只把下面内容作为必答问题：

1. 这场会议属于哪个项目？
2. 会议实际发生日期是什么？

会议主题、地点、材料类型、参会人、owner 和 due 由 Agent 先从材料中提取。提不出来时，写 `unknown` 或放入待确认项，不阻塞初稿；但会议实际日期不明确时必须停止并询问，因为它影响知识排序。

Agent 应回显自动识别结果，例如：“我识别主题为 X，材料类型为 transcript；如果不对请告诉我。”回显不等于强制用户先回答。

### 邮件来源补充

邮件是可选来源证据，不是默认监控对象。当前版本只定义来源 artifact 协议和 Agent 处理边界，不提供通用邮箱检索 adapter。Agent 不主动扫描邮箱、不建立后台邮件监控，也不默认同步邮件服务。

只有用户明确提出检索请求时，Agent 才能按用户给出的范围查找邮件，例如：

- 某个明确标题或近似标题。
- 某个发件人、收件人或账号。
- 某个时间范围。
- 用户提供的 `.eml`、截图、转发文本或粘贴邮件内容。

普通版中，Agent 可以把用户提供的邮件，或通过当前可用工具按用户指定范围检索到的邮件，整理为来源 artifact，默认保存摘要、元数据、关键事实和项目影响，不默认复制完整邮件正文。完整邮件正文、附件或导出文件只有在用户明确要求时才保存，并按项目 artifact 策略登记。

DIY 版未来可以进一步配置不同邮件来源适配器，例如 Apple Mail、Gmail、Outlook、导出的 `.eml` 或本地邮件归档。Apple Mail 只是本地可读来源之一，不是 `project-knowledge-officer` 的核心依赖。邮箱 adapter 的实现开口记录在 [future-todos.md](future-todos.md)。

## 模式转换

模式转换首先是 Agent 交互协议的转换，其次才是项目结构能力的转换。

### 普通版转 DIY 版

- 不改变已有会议事实。
- 不改写已有 decisions、todos 或 open questions 的含义。
- 只增加可配置表面和解释文档，例如 taxonomy、领域知识、模板或协作策略。
- 转换前先运行项目校验；转换后生成或更新项目使用说明，让之后的 Agent 知道按 DIY 版协作。

### DIY 版转普通版

- 不删除配置、历史、领域知识或 Git 历史。
- 不改写已有 decisions、todos 或 open questions 的含义。
- Agent 重新接管执行细节，只向用户暴露普通版 4 个概念和必要确认。
- 转换前后都要校验项目状态，保留现有可追溯来源。

## 内部 profile 兼容

脚本和模板中现有的 `minimal` / `advanced` profile 暂时保留：

- `minimal` 是普通版的能力底座。
- `advanced` 是 DIY 版可以启用的结构能力扩展。

用户文档和 Agent 对话应优先使用“普通版 / DIY 版”。只有在解释脚本参数、配置字段或兼容行为时，才需要提到 `minimal` / `advanced`。
